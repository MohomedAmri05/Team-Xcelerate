# High Street – Full-Stack Vehicle Sales Platform

High Street is a full-stack vehicle sales platform built for High Street (PVT) Ltd., Katugastota, Kandy, by Team Xcelerate (KND_05).

It has:

- a responsive public showroom;
- customer accounts with enquiries, test-drive bookings, complaints, finance applications, private documents and a wishlist;
- role- and permission-based staff operations;
- an Admin dashboard with reports and exports, an email outbox and an audit log;
- a financing calculator.

> **October 2026 upgrade.** This version adds complaint management, secure document uploads, a reporting centre with CSV/Excel/PDF export, a reliable email outbox with reply threading, an overview dashboard, notifications, and a new visual design. Your existing database is upgraded with two new migrations and none of your records are changed. Every team member now owns **four complete CRUD resources (16 in total)**; see [The 16 CRUD resources](#the-16-crud-resources-4-per-member). See [What's new](#whats-new-in-the-october-2026-upgrade), [Upgrading an existing database](#upgrading-an-existing-xampp-database) and [Testing report](#testing-report).

## Architecture

```text
React / Vite (client/)
    ↓  Axios — access token in the Authorization header, automatic refresh
Express REST API  /api/v1  (server/src)
    ↓  routes → auth / permission / rate-limit / validation middleware
Controllers  →  services (mail, reports, exports, files, activity log)
    ↓
Sequelize ORM  →  MySQL / MariaDB
                    ↘ private document storage (server/storage/documents)
                    ↘ public vehicle images     (server/uploads)
Background email worker (retries the outbox every 60 seconds)
```

## What's new in the October 2026 upgrade

### Complaint management (new module)

- Customers file complaints, optionally linked to a vehicle, enquiry or booking they own. They can attach evidence (PDF/images/Word), follow a status timeline and progress bar, reply, and confirm or reopen a resolution within 30 days.
- Each complaint gets a reference of the form `HS-CMP-2026-00001`.
- Staff with the new **Manage complaints** permission, and Admins, can:
  - triage, assign, set priority, change status (only allowed transitions);
  - reply to the customer, or add internal notes the customer never sees;
  - close a complaint; Admins can also delete one.
- Every change is stored in `complaint_status_history`, and customers are emailed on replies and status changes.

### Secure document uploads

- Customers can upload documents to their bookings, enquiries, complaints or general profile (e.g. driving licence, NIC, payslip for financing). They can view, download, rename, recategorise and delete them.
- Staff and Admins can see documents for records they are allowed to manage.
- The file type is checked from the file's **contents** (magic bytes), not just its name. Accepted types: PDF, JPG, PNG, WebP, DOCX; maximum 8 MB.
- Files are stored **outside** the public folder under random names, and are served only to authorised users, with `nosniff` / `attachment` / `no-store` headers.

### Reports (Report Generation component)

- 11 report types: vehicle inventory, vehicle demand, enquiries, test-drive bookings, complaints, users, sessions, documents, email delivery, the activity log and finance applications.
- Each report has filters (date range, status, make, etc.), summary cards, breakdown charts, a sortable table, printing, and **CSV / Excel / PDF** export.
- Reports can be saved and reused. Quick presets: this month, last 30 days, and so on.
- Staff see only the reports their permissions allow.

### Database component

- One new migration adds:
  - 8 tables: complaints, complaint messages, complaint status history, documents, email logs, inbound emails, activity logs, saved reports;
  - one permission column;
  - supporting indexes.
- Foreign keys, unique keys and CHECK constraints protect integrity.
- The migration is fully reversible, and rolling it back removes only what it added.
- Full documentation is in `docs/DATABASE.md`.

### Email fixed and made reliable

- Every email is recorded in an **outbox** (`email_logs`) with an honest status:
  - **Queued**, **Sending**, **Accepted** (the SMTP server accepted it), **Failed** (with the error) or **Preview** (SMTP not configured, so nothing was sent).
- Failed emails are retried automatically with increasing delays, and Admins can retry them manually.
- A dedupe key prevents the same message being sent twice.
- Customer emails carry a `Reply-To` pointing to your support mailbox, and a reference tag in the subject (`[HS-ENQ-12]`, `[HS-CMP-2026-00001]`, `[HS-TD-4]`).
- Staff notification emails use the customer's address as `Reply-To`, so staff can reply directly.
- New emails: enquiry acknowledgement, booking request/confirmation/changes, complaint updates, welcome email, password-change alert.
- **Inbound replies (optional):** an email provider webhook can post customer replies to `/api/v1/inbound/email`. They are matched to the enquiry or complaint by the subject tag and added to the conversation.
- The Admin **Email** tab shows the configuration and outbox, and can verify the SMTP connection and send a test email.
- The old behaviour of an enquiry response staying a Draft when delivery fails is kept.

### Dashboard, search and UI/UX

- New **Overview** dashboard:
  - live counts, items needing attention, recent activity;
  - grouped tabs with badge counts;
  - deep links (`/admin?tab=complaints`).
- Admin lists have search with **search history**, filter chips, sorting, pagination and **table/grid** views.
- A notification centre (bell icon) for customers and staff, refreshed every 60 seconds.
- Status badges, progress steps for bookings, enquiries and complaints, toasts, and confirmation dialogs (replacing browser `confirm()` pop-ups).
- New colour scheme:
  - deep green with a warm amber accent, not blue-only;
  - accessible contrast, visible focus rings, skip link, reduced-motion support;
  - responsive to 360 px phones.
- **No invented contact details.** Phone, WhatsApp, email and address are shown only if an Admin has entered them in Company Content. Otherwise the page says the details are not available.
- Customers can reschedule pending bookings, and see My Complaints and My Documents pages.

- A vehicle cannot be archived while it has an active test drive or an open finance application; the Admin sees the reason.

The application includes:

- Password hashing with bcrypt.
- Short-lived JWT access tokens.
- Hashed rotating refresh tokens.
- Revocable user sessions.
- Role-based authorization.
- Staff permission checks.
- Customer record ownership checks.
- Zod request validation.
- Helmet security headers.
- Restricted CORS configuration.
- Login and enquiry rate limiting.
- Image MIME-type validation.
- Image size and quantity restrictions.
- UUID image filenames.
- Protection against deactivating the final active Admin.
- Protection against deleting the active financing configuration.
- Soft archiving for vehicles.
- Draft response protection when email delivery fails.

The upgrade adds two more CRUD resources: **Complaints** (with messages and status history) and **Documents**. It also adds **Saved Reports**, and read/retry management of the **Email outbox**.

Additional security in this upgrade:

- File-content (magic-byte) validation for images and documents.
- Private document storage, authorised downloads only, path-traversal-safe storage keys.
- Per-record access rules for documents and complaints; internal complaint notes are hidden from customers.
- CSV/Excel export protection against spreadsheet formula injection.
- Inbound email webhook protected by a shared secret and rate limiting, disabled when no secret is set.
- Rate limits on complaint creation and the inbound webhook.
- Test emails can be sent only to the signed-in user's own address or the configured admin address.
- Login/registration errors do not reveal whether an account exists. (This was already the case and is kept.)
- No credentials are stored in the source code. Secrets come only from `.env`. The demo seeders' hard-coded admin, staff and customer passwords were replaced by `SEED_ADMIN_PASSWORD` / `SEED_STAFF_PASSWORD` / `SEED_CUSTOMER_PASSWORD`. ## Upgrading an existing XAMPP database

Your existing data is kept. The four new migrations, `202610110001`, `202610110002`, `202610150001` and `202610160001`, only **add** tables, columns and indexes. They do not change or delete existing rows. The exceptions: `202610150001` fills the two new permission columns from the existing ones, so that nobody loses access; `202610160001` allows `enquiry_responses.admin_id` and `documents.uploaded_by` to be empty, so a deleted Staff member's replies and files are kept.

1. **Back up first** (XAMPP shell or PowerShell in `C:\xampp\mysql\bin`):

   ```powershell
   .\mysqldump.exe -u root --routines --triggers high_street_db > high_street_db_backup_before_upgrade.sql
   ```

2. Apply the upgrade from the project folder:

   ```powershell
   npm.cmd --prefix server run db:migrate:status
   npm.cmd --prefix server run db:migrate
   ```

3. Optional demo data:

   ```powershell
   npm.cmd --prefix server run db:seed:templates
   npm.cmd --prefix server run db:seed:complaints
   ```

   - `db:seed:templates` adds five starter reply templates. It skips any that already exist.
   - `db:seed:complaints` creates complaints for the demo customer `customer@highstreet.lk`. If that account already exists, its password is **not** changed.

4. Give staff the new permission: Admin dashboard › Staff permissions › **Manage complaints**. Admins always have it. Reply templates are available to Staff with *Manage enquiries* or *Manage complaints*. Finance applications are Admin only.

To undo the upgrade, run `npm.cmd --prefix server run db:migrate:undo` once per new migration (four times for all four), newest first. This removes only the new tables, columns and `hs26_*` indexes. Complaints, documents and email history recorded since the upgrade are lost, so back up first.

## Email

### Sending through Gmail

1. Turn on 2-Step Verification for the Google account.
2. Create an **App Password** (Google Account › Security › App passwords). Never use the normal Gmail password.
3. Put the address in `SMTP_USER` and the App Password in `SMTP_PASS`.
4. Gmail only lets you send as that address (or verified aliases), so set `MAIL_FROM_ADDRESS` to the same address.
5. Restart the API.
6. In Admin › **Email**, click **Verify connection**, then **Send test email**.

### What the statuses mean

| Status | Meaning |
|---|---|
| Preview | SMTP is not configured. Nothing was sent; the message was printed in the API terminal. |
| Queued / Sending | Waiting for the background worker, or being sent now. |
| Accepted | The SMTP server accepted the message. This is **not** proof that it reached the inbox (spam filtering happens later). |
| Failed | Rejected or unreachable. The error is shown, retries are automatic (up to 3 attempts) and can also be done manually. |

### Customer replies

- Customer emails have `Reply-To: MAIL_REPLY_TO`, so replies go to your support mailbox. The subject tag (e.g. `[HS-CMP-2026-00001]`) tells staff which record a reply is about.
- To have replies appear **inside the app automatically**, connect an inbound-email provider (for example Mailgun Routes, SendGrid Inbound Parse, Postmark Inbound or Cloudflare Email Workers):
  1. Set `INBOUND_EMAIL_SECRET` to a long random value.
  2. Point the provider's webhook to `POST https://<your-api>/api/v1/inbound/email` with header `X-Inbound-Secret: <secret>`.
  3. Send a JSON body with `from`, `subject` and `text`.
- Matched replies are added to the enquiry or complaint. Unmatched ones are kept for Admin review in the Email tab.
- A plain Gmail inbox cannot call a webhook by itself, so it needs one of these providers or a small forwarding script.

## Known limitations

- Notifications refresh every 60 seconds (polling), not instantly.
- **Forgot password needs email.** Without SMTP settings, the reset link appears only in the API terminal (as "Preview"). On a real server, set up Gmail first.
- **Inactivity sign-out** runs in the browser. The server still ends sessions after `REFRESH_TOKEN_DAYS`, and a session can be revoked at any time.
- **The account lockout** (`LOGIN_LOCK_*`) is stored in the database. The separate per-computer rate limit (10 attempts per 15 minutes) is kept in memory and resets when the API restarts.
- Rate limits are kept in memory, so they reset when the API restarts and are not shared between multiple servers.
- Uploaded documents and images are stored on the server's disk. Back up `server/storage/documents` and `server/uploads` together with the database.
- On a fresh database, `db:migrate:undo:all` fails inside the original migration `202609130002` on Dolt, the MySQL-compatible server used for testing. It is expected to work on MariaDB, where that index exists, but this is not verified. The rollback of both new migrations was verified (the schema is identical to your backup afterwards).
- CSRF protection is not needed in the current design, because tokens are sent in the `Authorization` header, not in cookies. If you move tokens into cookies, add CSRF protection.
- "Accepted" email status means the SMTP server accepted the message, not that it reached the inbox.

## Production recommendations

- Use HTTPS, and high-entropy JWT secrets (two different 64-character random strings).
- Use a managed MySQL database with automatic backups. Back up the document storage too.
- Restrict `CLIENT_URL` to the deployed site.
- Use a transactional email provider (with SPF/DKIM set for your domain) and an inbound webhook for replies.
- Run `npm audit` and update dependencies.
- Remove or change all demonstration accounts and passwords.
- **Rotate any password that has ever been written in a shared file.** Never commit `.env`.
